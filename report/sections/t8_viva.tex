\subsection{Prepared answers}
\textbf{``What if I add a 5th resource dimension?''} Nothing in the code
changes. $d$ is read from the input (\texttt{Instance.d}). Every capacity
check loops over $k<d$, and $B$ averages over $d$ dimensions. Costs grow
linearly in $d$, from $O(n^2Kd)$ upward. Proofs: Lemma~\ref{lem:cert} and
Theorem~\ref{thm:sound} are per dimension, so they still hold. The bound
$B\le W/4$ is unchanged, because it is an average. One effect: an extra
binding dimension can only shrink $F(i)$, so there are more restarts and
more \texttt{NOT\_FOUND}s. The test \texttt{test\_five\_dimensions} shows
the 5th dimension deciding the placement.

\textbf{``What if two slots have different capacities?''} Already
supported. Capacities are stored per slot, $C(s)$, and every F2 check and
the L3 interval sum use $C(s)$. $B$ uses utilisation $\text{load}/C(s)$, so
a half-size slot at 50\% load counts as 50\%, not 25\%, and zero-capacity
cells are excluded. The test \texttt{test\_unequal\_capacities} covers it.
One subtlety: L1 (``task fits nowhere'') becomes more powerful, because a
large task may fit only in the big slots.

\textbf{``A decision you would make differently in hindsight?''} I would
build the local search around Kempe-chain interchanges from the start,
rather than single moves and pairwise swaps. Both the benchmark ratio of
1.141 and the tight example are 3-task traps that a Kempe move escapes.
I chose move and swap because they are simple to prove sound and cheap,
but they are exactly the neighbourhood the adversary exploits.
